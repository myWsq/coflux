# Coflux 2.8.0

**Agents can ask you for a secret without ever seeing it, and the local agent endpoint no longer answers web pages or other users.**

The runtime, the center, the desktop app and the command-line tools all change. Deploy the center and let the worker hot-upgrade before relying on secret requests; the endpoint hardening needs only the new worker.

## Highlights

- **`coflux secret` for API keys and passwords.** An agent in a Coflux terminal runs `coflux secret ask NAME --reason "..."` and waits. A card appears over that terminal on every desktop signed in to the account, showing the device, workspace and terminal, the name, and the agent's reason marked as the agent's own words. You type or paste the value into a masked field and choose Provide or Decline; closing the card cancels the request, and the first answer from any client wins. The agent only ever learns `provided`, `declined` or `cancelled`. The request also lands in the notification inbox, with the usual system notification.

- **The value goes straight to the device.** It travels from the desktop to the device's own worker over the same end-to-end encrypted device connection your terminal input uses; the center only relays that a request is pending. The worker keeps the value in memory, never on disk, bound to the terminal that asked, and forgets it when that terminal closes or the runtime restarts.

- **Using a secret without reading it.** `coflux secret exec NAME [NAME...] -- <command>` runs a command with each value in a same-name environment variable and prints `***` wherever a value would appear in its output. `coflux secret inject NAME --file .env [--key KEY]` makes the worker itself write `KEY=value` into a dotenv file inside the workspace; the value never passes through the agent. Where scrollback leaves the device, held values are also replaced by `***`: in `coflux terminal read`, in terminal reads through the account command line, and in the terminal snapshots the center stores. Your own live terminal is not masked.

- **Answer from the iPhone.** The iOS app marks a workspace whose agent is waiting for a secret, marks the terminal tab, and shows the same card at the top of that terminal. Voice input and the terminal input area never reach its field. There are no push notifications for these requests; the iOS build ships through TestFlight.

- **The local agent endpoint only serves Coflux terminals.** Local `coflux` commands and agent hooks now reach the daemon over a Unix socket where the operating system, not the request, says which process is calling. The loopback HTTP endpoint that older command-line tools still use now refuses any request with an `Origin` header or a `Host` other than the loopback address and port. A web page can no longer drive terminals through DNS rebinding. On Linux it also refuses callers running as another user.

## Install or update

**Mac:** install `coflux-2.8.0-arm64.dmg`, or use the desktop app's update action. The desktop app requires macOS 26+ and Apple Silicon.

**Linux and other headless machines:** the worker upgrades itself from the release. To update the command-line tools as well:

```sh
npm install -g cofluxd@2.8.0
cofluxd update
```

**iPhone:** install the TestFlight build that follows this release.

## Upgrade impact

- **Secret requests need the 2.8.0 center, worker and desktop app.** An older desktop never shows the card, so `coflux secret ask` ends as `cancelled` after its timeout (ten minutes by default) and says that the prompt may not have been shown. `ask` fails at once when the device is not connected to the center.
- **Agents started before the update keep working.** They keep the command-line tools they were launched with, which use the hardened loopback endpoint. Relaunching an agent moves it to the socket. A later release will remove the loopback path.
- **Anything else that called the loopback endpoint** with a browser-style `Origin` header or a different `Host` is now refused with `403`. Coflux's own tools never did.
- The wire protocol gains additive messages for pending requests and answers; no protocol version changes, and no database migration is involved.
- The supervisor is unchanged; no runtime restart is required.
