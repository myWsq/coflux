## Requirement

`apps/desktop` pins the astryx design system at `^0.1.6` (2026-07-15). Upstream
(`github.com/facebook/astryx`) is at `0.6.0` (2026-09-10) — 27 stable releases and
5 minors ahead. Nothing is broken today; the cost is accumulating drift: every
further month makes the jump wider, and the desktop client is meanwhile carrying
a hand-written workaround for an upstream defect.

Done means: `apps/desktop` builds, typechecks and passes its tests against
`@astryxdesign/core`, `/cli` and `/theme-neutral` at `0.6.0`, with every
breaking change between 0.1.6 and 0.6.0 that touches our call sites resolved,
and the repository's own design documentation telling the truth about what
0.6.0 does and does not fix.

This is not a redesign. No component gains or loses a visual role, no new
astryx component is adopted, and no UI is restyled beyond what the version
change itself forces. A reviewer should be able to read the diff as "same UI,
newer library".

## Decisions & tradeoffs

- **Upgrade all three packages to `0.6.0` in one step, keeping the caret range**
  (`^0.6.0`). Rejected: pinning exact versions — the repo's convention is caret
  everywhere in `apps/desktop/package.json`, and on a `0.x` line npm's caret
  already restricts to `0.6.x`, so a caret buys patch fixes without admitting
  `0.7`. Rejected: staged minor-by-minor upgrades — the cli ships every
  transform from `v0.0.2` to `v0.6.0` in one package, so stepping buys nothing
  and multiplies install cycles.
  Based on: `apps/desktop/package.json:26-28`; `@astryxdesign/cli@0.6.0`
  `assets/codemods/transforms/` contains `v0.1.7`…`v0.6.0` directories.

- **Drive the migration with `astryx upgrade`, not hand edits.** The one call
  site that breaks is mechanical, and the cli's own transform is the
  authoritative spelling of the rename. Hand edits are the fallback only if the
  cli refuses to run; a hand edit that diverges from the codemod's output is a
  bug, not a style choice.
  Based on: `assets/codemods/transforms/v0.1.8/rename-avatar-size-scale.mjs`.

- **`<Avatar size="xsmall">` becomes `size="sm"` and nothing else changes
  visually.** The 0.1.8 rename kept every pixel value but shifted every name one
  rung: the old `xsmall` is 24px, and 24px is spelled `sm` in the new scale
  (`xsm` is 20px, the old `tiny`). If the avatar changes size on screen, the
  migration is wrong.
  Corrected while executing: this entry originally claimed `xsmall` → `xsm` at
  20px. That was wrong, and the cli's own transform is the authority — it emits
  `sm`. Verified against both versions' `resolveSize`.
  Based on: `account-footer.tsx:116`; `resolveSize` returns 24 for `xsmall` in
  `@astryxdesign/core@0.1.6` `src/Avatar/Avatar.tsx:83-84` and 24 for `sm` in
  `0.6.0` `src/Avatar/Avatar.tsx:115-116`.

- **The menu-trigger tooltip workaround stays.** `docs/design-guidelines.md:32`
  makes its removal conditional on two upstream facts, and **both were checked
  against 0.6.0 and still hold**: `DropdownMenu` still erases the trigger's
  tooltip while open, and `Button` still renders its tooltip node conditionally.
  Removing `menu-button-tooltip.ts` or collapsing the three call sites back onto
  `button.tooltip` would reintroduce the stuck-hover defect.
  Rejected: treating the upgrade as the trigger to delete the workaround — that
  was the hypothesis going in, and the source says no.
  Based on: `@astryxdesign/core@0.6.0` `src/DropdownMenu/DropdownMenu.tsx:488`
  and `:926` (`tooltip={isOpen ? undefined : button.tooltip}`);
  `src/Button/Button.tsx:795` (`if (tooltip) { … renderTooltip(tooltip) }`).

- **Correct the documentation's version claim instead of deleting the rule.**
  `docs/design-guidelines.md:32` currently says the workaround "exists only for
  the pinned 0.1.6", which becomes false the moment this plan lands. The rule
  and its mechanism stay; only the version statement is rewritten to record that
  0.6.0 was checked and still carries the defect, so the next reader re-checks
  upstream rather than re-deriving the mechanism.
  Based on: `docs/design-guidelines.md:13-32`.

- **The tooltip theme override is validated by the user on a real machine, not
  by this plan.** `main.tsx` overrides `components.tooltip.base` and its comments
  reason explicitly about Tooltip's two-layer DOM and an inner StyleX
  `:not(#\#)` specificity of (0,5,0) that a single class cannot beat. Upstream
  guarantees the semantic `defineTheme` key, never the inner DOM. No typecheck or
  unit test can observe the result.
  Rejected: an agent-side visual check — the repo's standing convention is that
  desktop UI changes are accepted by the user, not walked through by an agent.
  Based on: `main.tsx:59-66`; `Tooltip.tsx:336` in 0.6.0 still wraps children in
  a `display:contents` div and delegates the visible surface to
  `renderTooltip`, so the two-layer shape persists but its inner styling was
  not verified.

- **Leave plan 111 alone.** The desktop confirm-dialog work lives unmerged on
  `dev/20260911-desktop-confirm-dialog`. 0.5.0's unified dismissal stack plausibly
  simplifies it — a `purpose="required"` Dialog now swallows Escape without the
  press reaching layers beneath — but acting on that from this branch would edit
  code this branch cannot see.
  Based on: `DialogPurpose = 'required' | 'form' | 'info'` unchanged between
  0.1.6 and 0.6.0 in `dist/Dialog/Dialog.d.ts`.

### Already surveyed and excluded — do not re-investigate

Each was checked against our call sites during exploration and does **not** hit
us. Re-deriving these is wasted effort; contradicting evidence is a STOP.

| Upstream breaking change | Why it misses us |
| --- | --- |
| 0.6.0 stops emitting bare prop/state classes (`.primary`, `.sm`, `.checked`) in favour of `data-*` | `index.css:165-166` matches only the `[class*="astryx-"]` target prefix, which upstream keeps stable |
| 0.5.0 Banner drops `defaultIsExpanded` | All three Banners pass only `status`/`title`/`container`, no children |
| 0.4.0 renames menu divider types to `*DividerData` | We use the data literal `{type:"divider"}` (`sidebar.tsx:175`, `:307`, `:507`), never the type name |

| peer dependency bumps | 0.6.0 wants `@stylexjs/stylex ^0.19.0` and `react >=19.0.0`; we are on 0.19.0 / 19.2.7 |

## Direction

One sequential track; the milestones are **not** independent — M2 reads the
compiled result of M1. Do not fan this plan out.

### Milestone 1: the desktop app builds against 0.6.0

`@astryxdesign/core`, `/cli` and `/theme-neutral` are at `^0.6.0` in
`apps/desktop/package.json`, the lockfile is regenerated, and every call site the
version jump breaks is migrated — via `astryx upgrade` where a transform exists.

Determine the correct ordering of the dependency bump and the codemod run
yourself (`astryx upgrade --help` states what the cli reads to decide which
transforms apply). Whatever the order, the acceptance is the same: no
pre-0.6.0 spelling survives anywhere in `apps/desktop/src`.

Validation: `pnpm -C apps/desktop typecheck` -> exit 0.

## Landmines

- `apps/desktop/src/renderer/main.tsx:59-66` — the tooltip override's comments
  encode upstream implementation details (two-layer DOM; inner padding of
  `--spacing-1` / `--spacing-2`; a StyleX `:not(#\#)` specificity of (0,5,0)
  that `.astryx-tooltip` at (0,1,0) cannot override). These are not part of
  astryx's public contract and may have shifted across five minors. If tooltips
  look wrong after the upgrade, this block is the first suspect — but do not
  "fix" it speculatively: the user validates it on a real machine.
- `astryx upgrade` may select transforms from the *installed* core version. Bump
  first and the cli could conclude there is nothing to migrate, silently skipping
  `v0.1.8`'s Avatar rename. The grep in M1 is what catches that; treat a clean
  typecheck alone as insufficient evidence the codemod ran.
- `apps/desktop/package.json:26-28` lists all three astryx packages under
  `devDependencies`, not `dependencies` — they are bundled by `electron-vite` at
  build time. Keep them there; promoting them changes what `electron-builder`
  ships.
- The three menu call sites (`branch-menu.tsx`, `port-menu.tsx`,
  `notification-inbox.tsx`) landed in `ee711cc5`, one commit before this branch.
  They are the workaround's consumers, not upgrade fallout; a diff that touches
  them needs a reason recorded here.

## Scope

In scope:
- `apps/desktop/package.json`
- `pnpm-lock.yaml`
- `apps/desktop/src/renderer/**` — only where the version jump forces a change
- `docs/design-guidelines.md` — the version claim at line 32
- `pnpm-workspace.yaml` — added while executing. astryx 0.6.0 introduces a `postinstall` in core and cli that 0.1.6 did not have, and pnpm 11 treats an unruled build script as an install failure: without a decision recorded in `allowBuilds`, even `pnpm exec`'s dependency self-check exits 1 and every validation command goes red. `pnpm add` wrote the two placeholder lines itself; declining them (the script only prints an `astryx init` nudge) is the minimum that makes the upgrade runnable.
- `apps/desktop/.claude/CLAUDE.md` — added while executing. The file carries an `<!-- ASTRYX:START -->` block that the cli generates and refreshes on `upgrade --apply`; it states the installed version and component count, so leaving it at 0.1.6 would make it lie.

Out of scope:
- `apps/desktop/src/renderer/components/workbench/menu-button-tooltip.ts` and its three call sites — the workaround stays; both upstream removal conditions still hold in 0.6.0
- Adopting anything new in 0.6.0 (`BottomSheet`, `Stepper`, `ComplexSelector`, `Indicator`, `i18n`, theme `adaptations`, `Collapsible.chevronPosition`) — separate work, separate plan
- `dev/20260911-desktop-confirm-dialog` (plan 111) — unmerged; the dismissal-stack simplification is evaluated when that branch merges
- `apps/server`, `apps/ios`, `packages/**` — no astryx usage
- Releasing, packaging, or deploying

## STOP conditions

- A fact cited under Decisions & tradeoffs no longer holds — in particular, if 0.6.0's `DropdownMenu` or `Button` turns out **not** to contain the tooltip-erasing code, because then the workaround's fate changes and that is a user decision, not an executor's.

## Maintenance notes

The workaround in `menu-button-tooltip.ts` is the thing to keep watching. Its
retirement condition is recorded at `docs/design-guidelines.md:32` and was
re-checked at 0.6.0 (still needed). Anyone doing the next astryx upgrade should
re-run that same two-part check against upstream `src/DropdownMenu/DropdownMenu.tsx`
and `src/Button/Button.tsx` before touching the call sites.

0.6.0 also brings things this plan deliberately declines: a unified overlay
dismissal stack (one Escape closes exactly one layer, with IME composition
handled — relevant to Chinese input), theme `adaptations` for viewport/pointer/
contrast/motion, `Collapsible.chevronPosition="start"` for tree-style rows, and
a large batch of Chat-surface fixes. Each is a candidate for its own plan.
